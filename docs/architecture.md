## Layers

1. **Systems** produce a `Trajectory`: times `(T,)`, positions `(T, n, 2)`, a `Box`. The
   reference system does so directly; a graph system does so through a *projection*.
2. **Graph systems** are a static `Space` (a graph whose nodes carry 2D coordinates and whose
   edges are stored as a dense neighbour table), the static velocity lattice, a `WalkerGraph`
   state (which site and which velocity node each ball is attached to) and rules that rewrite
   the ball hyperedges. `WalkerSystem` applies a rule set step by step and records a
   `GraphHistory`; `GraphHistory.project()` turns it into a `Trajectory`.
3. **Comparison** consumes two trajectories recorded at the same times and runs checks, each
   with an explicit threshold (`docs/comparison-method.md`).
4. **Experiments** tie a reference system and a graph system to one configuration, with the
   physical parameters derived once (`D = a^2 / (4 tau)`).
5. **Presentation** (HTML report, browser GUI) only consumes experiment results. Numerical code
   never imports presentation code.

## Rules of the code base

- Numerical cores depend on numpy and scipy only; networkx is imported lazily for graph views.
  This keeps the same modules running under pytest and under Pyodide.
- Randomness is explicit: every function that draws random numbers takes a
  `numpy.random.Generator`. Experiments spawn independent streams per system from one seed.
- Vectorised updates: one rule application is numpy work over all balls (the chain rules) or
  over all candidate matches (the generic matcher); the only Python loops are over the few
  contacts of a round. Space graphs expose a neighbour table `(num_nodes, degree)` for that.
- The physical meaning of a graph system is stated in code: `lattice_hop_diffusion()` is the
  formula the experiment uses to run the reference with the matching diffusion coefficient.

## The first graph system in detail

- Space: `L x L` square lattice, spacing `a`, node `(i, j)` at `(i a, j a)`. Boundary nodes get
  self-loops for the neighbours they lack, so every node has four hop options. With self-loops
  the uniform distribution over nodes is stationary, which matches the uniform stationary
  density of Brownian motion in a box with reflecting walls.
- The box of the projection extends `a / 2` beyond the outer nodes so that every node owns a cell
  of area `a^2`.
- State: the graph with space nodes `0 .. L^2 - 1` and walker nodes `L^2 .. L^2 + n - 1`, each
  walker joined to the space by one hyperedge `{w, anchor[w], velocity[w]}`; the random walkers
  of this system are balls at rest (velocity `o`).
- Rule `RandomHop`: for every walker, pick one of the four edges at its anchor uniformly at
  random and move the walker edge along it. Synchronous update of all walkers.
- Initial condition: all walkers at the centre node; the reference starts all particles at the
  centre of the box.
- Projection: a walker sits at its node's coordinates. For distribution tests, each walker gets
  a fixed random offset inside its node's cell (`GraphHistory.project(cell_rng=...)`): the graph
  then claims to imitate the reference at resolution `a`. Displacements, and therefore the MSD,
  do not depend on the offset.

## Metrics: energy, momentum, entropy (`imigraph.metrics`)

Overdamped Brownian particles exchange energy and momentum with the bath, so neither is
conserved particle by particle; the *ensemble* values are stationary and that is what is
measured, for both systems alike:

- **Kinetic energy per particle** `m |dr|^2 / (2 dt^2)` averaged over particles at every
  simulation step (free value `2 m D / dt`, the temperature of the bath in these units).
- **Total momentum** `m sum(dr) / dt` at every step (mean zero, standard deviation
  `sqrt(2 n m^2 D / dt)` per component).
- **Occupancy entropy** `-sum p ln p` of a `bins x bins` histogram at every recorded frame
  (0 at the start, `ln(bins^2)` for a uniform occupancy; rises on average, fluctuates).

Two rule-level metrics complete the picture:

- **Wall interaction rate**: fraction of particles per step that were reflected (reference) or
  hopped along a self-loop (graph). Zero until the cloud reaches the walls, then stationary;
  the two systems discretise the wall differently, so the rates are similar but not identical.
- **Occupied cells** of the lattice grid (a walker occupies the cell of its node): rises from 1
  towards `cells^2 (1 - exp(-n / cells^2))` for a uniform occupancy, equally in both systems.

Energy and momentum come from a `StepObserver` the simulators call after every fine step,
then averaged per recording interval, because a particle that bounces off a wall between two
recorded frames would otherwise look like it lost energy. Walls do cost a little: in the
default experiment both systems sit about 2% below the free value, stationary, and agree with
each other within 1%. `tests/test_metrics.py` pins these statements.

## Second reference system: the hard-disk gas (`imigraph.reference.gas`)

Energy-conserving particle motion: disks in straight lines, elastic collisions resolved at the
exact time of impact (the pair is moved back to contact, the velocity components along the
line of centres are exchanged, which conserves momentum and kinetic energy exactly, and both
move on), specular or periodic walls, fixed time step. `imigraph.experiments.gas` runs a free
expansion from the left half of the box and checks against kinetic theory: energy constant to
rounding, momentum constant (periodic) or bounded (specular walls), final speeds
Maxwell-Boltzmann (Rayleigh with `sigma^2 = E / (n m)`), occupancy entropy rising to the
uniform value. Page: `python -m imigraph gas-report`, which also runs the graph imitation below.

## The one walker: the ball `{w,s,v}` (`graph/state.py`, `graph/velocity.py`)

There is one kind of walker. A *ball* is the hyperedge `{w, s, v}`: walker node `w`, the site
`s` it sits on, and its velocity `v`, a node of the *velocity lattice*, the square lattice of
integer vectors `(vx, vy)` in cells per step with the same direction labels `+x, -x, +y, -y`
on its edges as the room. The origin `o` is rest: a ball on `o` is the random walker of the
Brownian imitation; a ball on a unit vector is the walker of the lattice gas; a ball with any
integer velocity is a ball of the ball gas. A ball may have a *body*, the lattice points within
`radius` of its site, which moves rigidly with it. `WalkerGraph(space, anchors, velocities,
radius)` is the state; `velocities=None` means every ball rests. The velocity lattice is never
stored: a rule reads it through the relations of the rule language (below) and the matcher
enumerates its nodes up to the system's `max_speed`.

## Rules as data: the notation (`graph/rules.py`)

`RuleSpec` is a rule as plain data: `lhs` / `rhs` edge lists over variables (walkers start with
`w`, velocities with `v` or are `o`, the rest are sites; `types` can override) with one
annotation per edge (`lhs_ops` / `rhs_ops`), direction `weights` for drawn edges, and
`self_loops` (`allow` / `forbid`). The text form is parsed and printed (`RuleSpec.parse`,
`.notation`); the JSON form (`to_dict` / `from_dict`) is what the GUI exports. The edges:

| edge | meaning |
| --- | --- |
| `{w,s}`, `{w,s,v}` | a ball on site `s` (velocity unnamed and kept), a ball with velocity `v` |
| `{w,s,v}_k` | the same, `k` bound to the direction of the ball's next hop in this step |
| `{s,t}` | a room edge from `s`, its label drawn with the weights (the chain rules) |
| `{s,t}_k`, `{s,s}_k` | the room edge of label `k` from `s`; a wall self-loop along `k` |
| `{s,x}_k1, {t,x}_k2` | the next hops of two balls *meet* at `x`: a contact |
| `{s,t}=d` | `d` is the lattice direction of the line from `s` to `t` (axis or diagonal) |
| `{v,v'}_k` | `v' = v + e_k`, an edge of the velocity lattice |
| `{v,v'}=d`, `{v,v'}>d` | `v'` on the line through `v` along `d`; `v'` ahead of `v` along `d` |
| `{v,v'}\|k`, `{v,v'}\|o` | the mirror image across the axis of `k`; the point mirror `-v` |
| `{v,v'}^` | a quarter turn, either sense at random |
| `d^`, `-k` | the perpendicular of `d`, the opposite of `k` |

Two families. The *chain* family (one ball `{w,s}` without velocity, drawn site edges, the
walker re-attached to a chain site) is run vectorised by `ChainRule`; `chain()` validates it,
`drift` / `diffusion` predict its physics (`tests/test_rules.py`). Everything else is a *ball*
rule, compiled by `BallPlan.compile` (balls, the steps of the match in order, the unknown
velocities, what every ball ends with; every message says what to change) and executed by the
generic matcher `BallRule.match`: candidate rows are the active balls (one-ball rules) or the
contact pairs (two-ball rules), the steps bind sites and directions row by row, and the
velocity variables not bound by a ball are *solved* by enumerating the velocity lattice and
keeping the nodes that satisfy every relation (no node: no match; several: one drawn at
random). The library (`STREAM`, `REFLECT`, `EXCHANGE`, `SWAP`, `TURN`, `KICK`) is written in
the notation; the elastic exchange is the rectangle spanned by the two velocities, the wall a
mirror, the HPP collision a quarter turn, and none of them is a formula in the code.

A *rule set* is a tuple of such rules; `rules_from_data` builds it from the request's list.

## The walker system: rounds, contacts, waiting (`graph/world.py`)

`WalkerSystem(space, rules, step_time, overlaps, max_speed, mass)` runs a rule set on balls. A
step: every ball gets a hop budget `|vx| + |vy|` with its hops in Bresenham order; the *round
rules* (whose balls carry a hop label: Stream, Reflect, the collision rules) are applied in
order in every round to the balls with hops left, each seeing the state the previous one
produced, until no ball has hops left (a cap of `2 max + 2` rounds); then the *step rules*
(chain rules, Kick) run once each. A ball that moves to its hop target consumes a hop; a ball
whose velocity changes mid-step continues with the tail of its new hop order, never more hops
than it had. `round_context` is the matcher's view of a round: a ball that cannot move (no hops
left, blocked by a wall) *stays*; two balls whose hops meet (land on one site, land on a staying
ball, or cross) are held back, and a ball landing on a held ball is held too, until nothing
changes; held pairs that approach each other are the *contacts* a collision rule matches; a
ball still held when Stream runs waits in this round. So no two balls ever share a site, and a
collision rule is re-applied within a round while it finds new contacts (a redirected ball may
meet a third). `GraphHistory` records anchors, velocities, visited sites and the events
(collisions and bounces with the rule's name and the velocities before and after); it reports
energy, momentum, entropies, exact `checks()` and `captions()`. Balls at rest under chain rules
reproduce `RuleSequence` step for step (`tests/test_world.py`).

*Overlapping matches.* A chain rule's matches overlap when they share a site edge; the
`overlaps` strategy decides which are applied in a step (`select_matches`): `parallel` applies
all, `ordered` / `random` / `oldest` apply a greedy non-overlapping set in walker-index order, a
fresh random order, or longest-waiting-first, and the skipped walkers wait. The same strategy
orders contact pairs when a ball is in several (one collision per ball per round).

## The lattice gas and the ball gas (`graph/gas.py`, `graph/balls.py`, `experiments/balls.py`)

`LatticeGas` is the HPP preset: balls with unit velocities under Reflect, Turn, Swap, Stream
(head-on pairs turn by a quarter turn at the contact; other meeting pairs swap velocities, a
deflection where HPP's point particles would pass through each other and share a site). It
returns the same `GasRun` as the hard-disk gas, so the energy, momentum, entropy and Maxwell
checks apply to both; `imigraph.experiments.gas.run_gas_comparison` runs both from the left
half of the unit box at the same recording times. Known limits, stated on the page: a single
speed (no Maxwell-Boltzmann distribution, the check is informative) and the anisotropy of the
square lattice (FHP on a hexagonal lattice is the fix; `Space` is the seam).

The ball gas (`experiments/balls.py`) runs balls with integer velocities under a collision
rule set: `exchange` (Reflect, Exchange, Swap, Stream: the elastic collision of equal masses,
exact along an axis and for even diagonal hits, Swap taking the odd diagonal hits), `swap`
(every hit head-on), `hpp` (the lattice gas's set), or `custom` with any rule list (the
playground's). `run_ball_comparison` starts the hard-disk gas of `reference/gas.py` exactly
where the balls start, with their velocities and disks covering their cells, records it at the
lattice steps, applies the gas checks to both and `compare()` to the projection of the graph
system against the reference. The GUI section "Balls bouncing in a room" shows the graph, its
2D projection and the reference side by side with captions, the checks tables, the charts and
the rules of the run with their patterns (`report/balls.py`, `live.balls`).

## The playground and its saved page

`report.live.playground(request)` runs a small world from a *starting universe* (`size`,
`walls` reflecting or periodic, `walkers`, `placement`: centre, corner, random, left half,
explicit `sites` clicked in the GUI, or the two-ball presets head-on and diagonal; the balls'
`velocity`: rest, unit or random up to `max_speed`, or explicit `velocities`; `radius`) with a
rule set, records every state, every visited site and every event, and returns the rule
descriptions (each with an SVG `pattern` of its two sides, `report.svg.rule_pattern`, sites
grey, walkers red, velocities blue, annotations on the edges), the resolved universe, the
captions and the measured drift, diffusion, wall rate, occupancy, collisions, bounces,
momentum and energy next to the specs' prediction. `report.playground.build_playground_page`
turns that into one self-contained page (`assets/playground.html`); the GUI builds it in
Pyodide (*Save result page*) and `python -m imigraph playground-report --request-file
session.json` builds it from the session JSON the GUI exports, as a new timestamped
`output/playground_*.html`. The GUI's rule editor (`web/app.js`) is two views of one
`RuleSpec`: the drawing (nodes are the variables, each side its own edge set, annotations
shown on the edges, same layout as `rule_pattern`) and the notation text; validation stays in
Python (`RuleSpec.chain()` / `BallPlan.compile`), the editor shows its message. The
explanation of the ball, the two lattices and the rule library lives in
`report/assets/collisions.html` and is shown in the GUI and on the saved page.
`report.bundle.write_gui_page` (`python -m imigraph gui-page`) inlines the stylesheet, `viz.js`,
`app.js` and the project wheel (base64) into `web/index.html`, giving `output/rule_editor_*.html`:
the GUI as one file that opens from `file://` (only Pyodide comes from the CDN), the form in which
it is published to imigraph-reports.

## Extending

- **New space**: implement the `Space` protocol (`coordinates`, `neighbors`, `box`,
  `cell_size`, `edges()`, `to_networkx()`). Keep the neighbour table dense (pad with self-loops
  or implement a weighted choice in the rule). Bodies and captions need a square lattice.
- **New rule**: write it in the notation (a preset in `web/app.js`, a constant in
  `graph/rules.py` with its texts in `LIBRARY_TEXTS`) and test what it conserves; a new
  *relation* of the velocity lattice is a new annotation: parse it in `DirRef` / `_EDGE`,
  validate it in `BallPlan.compile`, evaluate it in `BallRule.match`, draw it in
  `svg.rule_pattern` and `web/app.js`, document it in `assets/collisions.html`.
- **New reference system**: return a `Trajectory`; document the analytic facts the tests use.
- **New check**: implement `Check.run(reference, candidate) -> CheckResult` and add it to the
  validation matrix in `tests/test_compare.py` (a pass case and at least one fail case).
- **Growing spaces** (the next step towards the Wolfram model): a rule that also adds nodes and
  edges needs a mutable space; the projection should then come from the graph itself (for
  example a spectral embedding of the graph Laplacian) instead of being given a priori.
